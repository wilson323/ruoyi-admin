## 六、本会话蜂群派单衍生 — 不可执行项(W5 新发现)

> 来源:第五轮蜂群派单(A23/A24/A25/A26,2026-09-07)
> 性质:在四轮治理闭环基础上,**新增**一批"前端可执行范围内已闭环,但仍需后端验证/确认"的衍生卡

### 6.1 A23 disposition 标注的"后端已交付前端无 UI"清单

> A23 在处理剩余 15 个零引用权限码时,**明确区分**两种零引用:
> 1. 前端漏接(应接入) → A13/A23 已完成
> 2. 后端已交付但前端**没有对应 UI 需求** → 用 `/* reserved */` 标注,常量保留

**预计 ~10 个码**(`apps/web-antd/src/views/ipd/_shared/ipd-permission-codes.ts` 中以 `reserved: true` 标记或 `/* reserved */` 注释):

- `PROJECT_STATUS_CHANGE` (`ipd:project:status-change`) — 项目状态变更(后端已交付,前端无对应 UI 入口)
- `PRODUCT_BIND_PROJECT` (`ipd:product:bind-project`) — 产品绑定项目
- `NOTIFICATION_READ` / `NOTIFICATION_DISPATCH` — 通知读/派发
- `COEFFICIENT_PROPOSE` / `COEFFICIENT_CONFIRM` — 系数提案/确认
- `COMPLIANCE_READ` / `COMPLIANCE_WRITE` — 合规读/写
- `SWITCHING_ACCEPTANCE_QUERY` / `SWITCHING_ACCEPTANCE_ADMIN` — 切换验收查询/管理
- `STAGE_ACTION_LIST` / `STAGE_ACTION_INSTANTIATE` — 阶段动作列表/实例化

**处置**:
- 全部用 `/* reserved */` 注释保留常量(不删除 — 业务侧后续若需要 UI 可直接接入)
- 静态契约扫描测试扩展:reserved 码不应出现于 `v-access:code` 指令(否则前端无 UI 时也会触发后端 403)
- 业务侧一旦提供,可由 A23 或后续 agent 直接接入,无需重新定义常量

**归属**: 仍属"前端可执行"范畴,**A23 已闭环**;不属本登记范围。

### 6.2 A24 覆盖补齐揭示的潜在后端契约风险

> A24 补齐 `demand.ts` + `workbench.ts` 的 0% 覆盖率时,写入了**三层单元测试**:
> 1. 参数 normalize(蜜罐字段 / 附件白名单 / 8 位查询码正则)
> 2. 响应 DTO 白名单字段
> 3. 错误传播(5xx/4xx/断网)

**事实陈述**:
- `apps/web-antd/src/api/ipd/demand.ts` 5 endpoint + `apps/web-antd/src/api/ipd/workbench.ts` endpoint 在 happy-dom 单测下**不连真实后端**
- 单元测试覆盖了**参数 normalize 与白名单 DTO**,如后端字段漂移,前端测试**会先红**
- 这等于把"后端契约守卫"嵌入了前端测试套件

**潜在风险**:
- 若后端**主动修改响应字段命名**(如把 `code` 改成 `queryCode` 类似 R1 历史教训),测试会先红,但**已上线用户会先遇到 4xx/5xx** — 测试是事后保护,不是事前协调
- 若后端**新增字段**而无文档同步,前端白名单 DTO 会**安全丢弃**新字段 — 业务可能因前端不读而漏功能
- 若后端**调整业务码**(如 40011 限频码改成 40012),前端 `ipdErrorText` 文案会**沉默兜底为"操作失败,请稍后重试"**,失去具体告警意义

**归属**:
- 仍属**前端可执行范围**(R13/R14 已闭环)
- 但**强烈建议**后端在修改契约前**先发跨仓信号**(本登记文件 §四模式),让前端同步调整 normalize / DTO / 文案表

### 6.3 跨仓 — 34 权限码全部接入后,后端必须保证 403 实际生效

**事实陈述**:
- A13(第四轮)接入 19 个权限码
- A23(第五轮)预计接入剩余 5 个 + reserved 标注 10 个
- **合计 34 个权限码**全部接入前端(19 active v-access + 5 active meta.access + 10 reserved 标记)

**风险**:
- 前端 `v-access:code` 指令 + 路由 `meta.access` 数组已**完整**
- 但**前端只是"看不见"按钮**,**真正的权限拦截在后端**
- 若后端 Spring Security / SaToken 配置**未 1:1 对应实现**,前端按钮隐藏但 curl/Postman 直接调用 API **仍可成功**
- 这等于**形同虚设的越权防御** — P1 安全风险

**后端必须保证**:
1. **所有 34 个权限码**在 Spring Security `hasAuthority('ipd:*')` 或 SaToken `@SaCheckPermission` 中**真实存在**
2. **403 响应码**必须稳定(不能改 401/200),前端才能稳定识别权限不足
3. **权限码字面值**必须与前端常量**逐字符一致**(`ipd:ai-model:list` 不能写成 `ipd:ai-model:query`)
4. **新增权限码**必须先经过 `apps/web-antd/src/views/ipd/_shared/ipd-permission-codes.ts` SSOT 登记,后端再实现,避免历史 19 零引用教训重演

**归属**: **本仓不可执行**,归后端会话 / owner 验证 — 建议后端起单卡"权限码 1:1 核对 + 403 集成测试",与 A13/A23 形成完整闭环
