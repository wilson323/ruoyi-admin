# IPD 前端权限三套体系边界（meta.access / meta.authority / v-access:code）

> **基线**: 2026-09-23 排查「研发招募/发起招标」按钮权限时发现——前端仓同时存在三套权限表达，部分形同虚设，团队易把三套混用而不知。本文档把三套的**消费点、真假消费、误判风险、修复方向**写实，避免后续漂移。
>
> **适用范围**: 仅前端仓 `apps/web-antd/`；后端 controller 端点本身已用 RBAC（详见 `docs/script/sql/开发说明/` RBAC 章节，本文不重复）。
>
> **不动代码**: docs-only 探针，不动 route/meta/组件，follow-up 见 §五。

## 一、三套体系速查

| 套系 | 表达位置 | 取值 | 当前消费点 | 真实运行态 |
|---|---|---|---|---|
| **meta.authority** | 路由 meta | `IpdPersonType[]`（如 `['SUPER_ADMIN']`） | `ipd-guard.ts:55-59 hasAuthority()` | ✅ 真消费 |
| **meta.access** | 路由 meta | 权限码字符串数组（来自 `PAGE_PERMISSIONS`） | **当前无消费者**（仅装饰） | ❌ 形同虚设 |
| **v-access:code** | 按钮属性 | 权限码字符串字面量（如 `'monitor:logininfor:remove'`） | `accessStore.accessCodes` + 指令逐码判定 | ✅ 真消费（仅对超管生效） |

## 二、三套边界（消费点 / 误判）

### 2.1 `meta.authority`（路由级 personType 闸）

- **定义位置**: `apps/web-antd/src/router/routes/modules/ipd.ts`（每条路由的 `meta.authority`）
- **消费位置**: `apps/web-antd/src/router/ipd-guard.ts:55-59`
  ```ts
  function hasAuthority(to: RouteLocationNormalized, identity: IpdIdentity): boolean {
    const authority = to.meta.authority;
    if (!authority || authority.length === 0) return true;  // 空数组 = 任何人都进
    return authority.includes(identity.person.personType);
  }
  ```
- **边界**: 路由级粗闸，personType 维度，仅判定「personType 是否在白名单」。
- **误判**: personType 白名单为空 → 任何登录用户都可访问，路由层无防护。

### 2.2 `meta.access`（路由级权限码，目前装饰）

- **定义位置**: 同上路由文件，常量在 `apps/web-antd/src/views/ipd/_shared/ipd-permission-codes.ts`
  ```ts
  // L153 附近：/ipd/bids 路由的 meta.access
  PAGE_PERMISSIONS['/ipd/bids']  // 含 BID_INVITATION_ADMIN_ASSIGN 等
  ```
- **当前消费点**: **无**。
  - `ipd-guard.ts` 的 `hasAuthority` 只读 `meta.authority`，**不读 `meta.access`**。
  - 路由守卫未消费 `meta.access`，**任何路由 meta.access 当前都是装饰性元数据**。
- **边界**: 路由级细闸（权限码维度），目前未实装。
- **误判**: 开发者看到 `meta.access: ['BID_XXX']` 会以为路由级做了权限拦截，**实际无任何运行时拦截**。所有「路由有 meta.access 即可保安全」的假设都是假绿。

### 2.3 `v-access:code`（按钮级权限码闸）

- **定义位置**: 各 Vue 模板按钮属性，如
  ```vue
  <!-- apps/web-antd/src/views/monitor/logininfor/index.vue:156 -->
  <Button v-access:code="['monitor:logininfor:remove']">删除</Button>
  ```
- **消费位置**: Vben 框架 `accessStore.accessCodes` + `v-access:code` 指令（逐码匹配）。
- **关键发现**: `apps/web-antd/src/store/vben-identity.ts:34-37 vbenCodesOf()` 决定 `accessCodes` 内容：
  ```ts
  export function vbenCodesOf(personType: string, scope: string): string[] {
    if (personType === 'SUPER_ADMIN') return ['*:*:*'];   // 超管全通码
    return [scope, `personType:${personType}`].filter(Boolean);  // ← 非超管无 IPD 权限码
  }
  ```
  - **SUPER_ADMIN**: `accessCodes = ['*:*:*']`，全通，所有 `v-access:code` 都过。
  - **MARKET_PM / RD_PM / GROUP_LEADER**: `accessCodes = [scope, 'personType:xxx']`——**没有 IPD 业务权限码**。
  - **结果**: 非超管用户的 `v-access:code` **全部不渲染按钮**（已实测：46 个页面全部不显示 add/edit/delete/export/import 按钮）。
- **边界**: 按钮级细闸（权限码维度），仅对超管生效；非超管的「按钮可见性」需要走组件内的 `auth.identity?.person.personType === 'XXX'` 自定义判定（这是 IPD 现状）。
- **误判**:
  1. 写 `v-access:code="['BID_XXX']` 期望非超管能按钮可见——**不会**，非超管 accessCodes 里没这个码。
  2. 把 `v-access:code` 当万能权限开关——它消费的是 vben 的 accessCodes，与 IPD 路由级 `meta.authority` 是两套隔离体系。

## 三、案例：`/ipd/bids`（研发招募页）

| 层 | 配置 | 是否真拦截 |
|---|---|---|
| 路由 `meta.authority` | 无（空数组） | ❌ 任何登录用户都能进路由 |
| 路由 `meta.access` | `['BID_INVITATION_ADMIN_ASSIGN', ...]` | ❌ 无消费者 |
| 按钮 `v-access:code` | 无（按钮判定走 `canCreateBid`） | ✅ 真消费 `personType==='MARKET_PM'\|'SUPER_ADMIN'` |

**实证路径**（RD_PM 用户登录）：
1. 进 `/ipd/bids` → `hasAuthority` 空数组 → 通过 → 进入页面 ✅
2. 看「发起招标」按钮 → `canCreateBid` 算 `['MARKET_PM','SUPER_ADMIN'].includes('RD_PM')` = false → 按钮 disabled + Tooltip 提示 ✅

**缺口**:
- 任何登录用户都能**进入** `/ipd/bids` 页面，仅按钮被组件内自判定算完才能导航到 `/ipd/bids/create`。
- 如果后端 `/api/v1/bid-invitations` POST 没做 RBAC，**直接 curl 可绕过**前端三套闸。

## 四、修复路线（与 R142 F1-F5 对齐，docs-only 设计）

| 优先级 | 修复 | 工作量 | 阻塞条件 |
|---|---|---|---|
| P1 | 路由守卫扩展：补 `hasAccess()` 读 `meta.access`，对 `accessCodes` 做精细匹配 | 0.5d | 后端 IPD 鉴权接口要产出真实 `ipd:bid:*` 权限码进 `accessCodes` |
| P1 | 后端鉴权接口接入真实业务权限码（`BID_INVITATION_ADMIN_ASSIGN` 等 19+ 码），不再只发 `personType:xxx` | 1d | 需后端 owner 拍板契约 |
| P2 | 抽 `permissions.ts` 把 `IPD_PERMISSION_CODES` 常量集中一处，给守卫和指令共用（避免 grep 漂移） | 0.5d | 无 |
| P2 | 把 `canCreateBid = computed(...)` 改成 `v-access:code` + 自定义指令 + accessCodes 真接入后的标准模式 | 1d | 依赖 P1 |
| P3 | drift-guard 加规则：路由 meta.access 不允许孤悬（必须能被守卫消费，或必须带注释 `// @decorative-only`） | 0.5d | 需改 `scripts/check-ipd-frontend-drift.sh` |
| P3 | 真活 e2e：RD_PM 用户 curl `/api/v1/bid-invitations POST` 必须 403 | 1d | 依赖后端 P1 |

**P1 不完成 → 三套体系任何一套都不可信**。

## 六、适用边界与不适用范围

- **适用**: 前端仓所有 IPD 视图与路由；任何写 `meta.access`/`meta.authority`/`v-access:code` 的 PR。
- **不适用**: 平台 admin 模块（`monitor/logininfor` 等），走的是 Platform 包络与 vben 原生权限体系，accessCodes 真含业务权限码（`monitor:logininfor:remove` 等），与 IPD 三套体系不互通。
- **不替代**: 后端 RBAC（Spring Security + IPD RBAC）的最终鉴权；前端任何一套闸失效时，后端仍是最后一道防线。
