## 为什么反复出错

### 把不完整检索升级成全局事实

原始证据 `/Users/mac/.claude/projects/-Users-mac-Documents-ruoyi-ai/62668c88-cc59-4db2-ad6e-81a7479158ec.jsonl`：

- 1066 行只显示前五条测试命中，1071 行却断言配置只在测试引用；1173 行找到生产常量读取，1178/1188 行撤回。不是配置缺失，而是检索方式漏掉常量间接引用。
- 1208 行截到前八条测试命中，1213 行断言生产引用为零；1331 行实际测试失败指向生产规则登记，1336 行承认 `head -8` 漏掉后续，1341 行回读登记源码。
- 857 行按类名引用数筛选控制器，862 行承认遗漏 Spring 注册机制，并把注释算成生产引用。

这三条说明同一失败模式：检索覆盖范围尚未证明，否定结论先出；错误前提又进入方案。不能用“没搜到”证明“不存在”。当前交叉核对可复跑：

当前方法/调用仍可读取，历史误报不是当前产品缺陷。以上原始记录只用于工程取证，不包含在业务提示词中。

### 没先定位用户指定入口，套用相邻功能的解释

当前 `apps/web-antd/src/views/ipd/_shared/ai-assistant.vue` 已调用项目面板 submitText，不能把旧缺口照搬到当前源码。设备安全案例因原始用户已授权全机检查，已排除为“未授权越界”证据，避免审计自身再制造错误归因。

### 工程验收、加载状态和业务结果被混用

已有 runner 明确只证明工程检查；运行包与业务验收字段为未验证。历史 10 月 3 日根因研究也明确全 IDE 强制拦截、真实加载和业务验收尚未闭环。因此重复出错不能归因于“没有任何门禁”，而是调用覆盖不完整、证据消费者越过了证明范围。

Codex 原始纠正索引：`/Users/mac/.codex/sessions/2026/10/04/rollout-2026-10-04T04-08-41-01a1069a-0e4c-7c61-8e97-efebd8544aea.jsonl:536` 用户质疑旧模型额度结论；历史后续实测成功与输出截断需分开。这只说明历史纠正，不证明目前任意供应商可用。

IAP 的历史范围记录指出编制阶段混入外部仓库，后来只增加“范围外”注释而未清掉执行计划；它不能当作当前 IPD 产品缺陷或当前 IAP 已修复的运行证明。

### 规则增加了，执行接口却没有同步收敛

本轮当前源码和反例确认：

1. runner 原来仅检查事项编号格式，未查原镜像存在性。
2. 本仓代码清单没有绑定仓外总画布、分节和部分被忽略的 IDE 配置；它们变化不会使旧 receipt 失效。
3. 前端 `.harness/verify.sh` 与技能导航没有进入验证器指纹。
4. Cursor 的画布检查器仍要求当前画布已移除的统计组件，同时接受另一检查器拒绝的 CLOSED；实跑当前合法画布反而被其拒绝。
5. Claude/Codex 的 Stop 提醒原来只是 echo/exit0，没有强制回读 receipt；Cursor 检查只涵盖特定编辑工具，不涵盖任意 Bash 写入。

第五项仍是未闭环的执行层边界，不能因为修了前四项就声称全 IDE 防线已完成。

## 已实际修改

- 沿现有 runner 查询原镜像的独立完整事项标签；虚构标签和已有编号的子串均拒绝，不另建任务注册源。此检查只证明标签登记，**不代替 allowedPaths 或业务授权**。
- 输入摘要加入原镜像、总画布/引用分节、既有指令和 IDE 配置的内容指纹；只存摘要，不复制秘密。计划/配置变更在执行中和执行后均使旧证据失效。
- 前端 verify 入口和技能纳入验证器身份。
- 两个画布入口复用 `scripts/check-ipd-plan-context.py` 的同一函数，按当前总画布的 OPEN/BLOCKED 合同检查唯一动作/解除条件；旧可选展示存在时必须一致。移除另一套旧规则和调试临时文件写入；非法 JSON/非对象输入拒绝。
- Ruflo 的依赖接口修复和单一初始化入口见 `../ruflo-installation-20261008.md`；移除重复 MCP 启动配置及旧静默补充分支。
- 本轮出现过原生向量测试 cwd 锁冲突，已改唯一临时目录；两个相同测试并发退出0，未通过重跑掩盖原始原因。
