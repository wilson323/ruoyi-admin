# 隐式依赖三反模式登记（R182 权限三套体系 + R184 RAG 真活触发三根因同构模式）

> **基线**: 2026-09-23 R185 元根因深化轮。R182（前端权限三套体系）+ R184（后端 RAG 真活触发三根因）两个独立事件深挖发现**同构元模式**：「配置/契约的隐式依赖被掩盖在 try-catch / 拦截器 / 守卫之后，运行态无信号、无门禁、无测试断言」。本文档把三反模式写实，给机制化修复方向。
>
> **适用范围**: 前端仓 `apps/web-antd/` + 后端仓 `ruoyi-modules/ruoyi-ipd/`；任何写「配置/拦截器/守卫/校验链」的 PR。
>
> **不动代码**: docs-only 探针，不动 route/meta/组件/Java/yml，follow-up 见 §六。

## 二、反模式 ① 配置存在但无消费者（M-Root-11）

### 定义
配置项（路由 meta / yml key / 注解）存在且被开发者认为「已生效」，但**运行态无任何消费者**读取它，或消费者读取顺序错导致配置被跳过。

### R182 实证：`meta.access` 装饰性
- **配置位置**: `apps/web-antd/src/router/routes/modules/ipd.ts:189-193`
  ```ts
  {
    component: () => import('#/views/ipd/bid/list/index.vue'),
    meta: { access: [...(PAGE_PERMISSIONS['/ipd/bids'] ?? [])], icon: 'lucide:handshake', order: 5, title: '研发招募' },
    name: 'IpdBids',
    path: 'bids',
  }
  ```
- **预期消费者**: 路由守卫 `ipd-guard.ts` 的 `hasAuthority()` 或新增的 `hasAccess()`
- **实际消费者**: **无**。`hasAuthority()` 只读 `meta.authority`，不读 `meta.access`。
- **后果**: 任何登录用户都能进 `/ipd/bids` 路由（`meta.authority = []` 空数组 ⇒ `hasAuthority` return true）。
- **假绿陷阱**: 开发者看到 `meta.access: ['BID_INVITATION_ADMIN_ASSIGN']` 会以为路由级做了权限拦截，**实际无任何运行时拦截**。

### R184 实证：`ai.allowed-hosts` 黑名单先于 allowlist
- **配置位置**: `application-ipd-local.yml` 的 `ai.allowed-hosts: "127.0.0.1,localhost"`
- **预期消费者**: `AiChatClient.validateEndpoint()` 的 SSRF 校验链
- **实际消费者**: 校验链**先检查黑名单**（throw）再检查 allowlist，本机 mock 走 127.0.0.1 直接被黑名单拦截。
- **后果**: 合法路径（127.0.0.1 mock）被拦，配置存在但优先级错。
- **修法**: allowlist 优先检查（host 等值匹配，命中即跳过黑名单 + DNS rebinding）。

### 修复模式
1. **drift-guard 检查孤悬配置**: 每个 PR 自动扫描「配置存在但无消费者」的孤悬项（如 `meta.access` 无 `hasAccess()` 读取）。
2. **优先级声明**: 多校验链并存时显式声明优先级（如 allowlist > 黑名单 > DNS rebinding），不允许隐式顺序。
3. **会红的测试**: 每个配置项必须有正例 + 反例测试，证明「配置被消费 + 消费正确」。

## 三、反模式 ② 隐式上下文丢失（M-Root-9）

### 定义
系统依赖隐式上下文（线程局部变量 / 拦截器栈 / 异步任务传递），但上下文在跨线程 / 跨拦截器 / 跨异步边界时**静默丢失**，导致配置/权限/租户等关键信息不可见。

### R182 实证：`accessCodes` 非超管丢业务码
- **上下文位置**: `apps/web-antd/src/store/vben-identity.ts:34-37 vbenCodesOf()`
  ```ts
  export function vbenCodesOf(personType: string, scope: string): string[] {
    if (personType === 'SUPER_ADMIN') return ['*:*:*'];   // 超管全通码
    return [scope, `personType:${personType}`].filter(Boolean);  // ← 非超管无 IPD 业务权限码
  }
  ```
- **预期上下文**: 非超管用户的 `accessCodes` 应含真实 IPD 业务权限码（如 `ipd:bid:create`）
- **实际上下文**: 非超管只拿 `[scope, 'personType:xxx']`，**无 IPD 业务权限码**。
- **后果**: 非超管的 `v-access:code="['BID_XXX']"` **全判否**，46 个页面 add/edit/delete/export/import 按钮全部不显示。
- **假绿陷阱**: 开发者写 `v-access:code` 期望非超管能按钮可见——**不会**，非超管 accessCodes 里没这个码。

### R184 实证：异步线程丢租户上下文
- **上下文位置**: `PlusTenantLineHandler.ignoreTable()` 理论忽略 `ai_model_configs`
- **预期上下文**: 异步线程应继承主线程的租户上下文（或显式忽略）
- **实际上下文**: 异步线程 / IPD StpLogic 上下文仍可能拼 `tenant_id IS NULL`，把 `tenant_id='000000'` 行过滤掉。
- **后果**: `currentEnabled()` 抛 STATE_CONFLICT（配置不可用），但真库有数据。
- **修法**: `AiModelConfigMapper` + `AiDocEmbeddingMapper` 类级 `@InterceptorIgnore(tenantLine="true")`，显式忽略租户拦截器。

### 修复模式
1. **上下文显式传递**: 跨线程 / 跨拦截器 / 跨异步边界时，上下文必须显式传递（如 `@InterceptorIgnore` 注解 / `TaskDecorator` 包装）。
2. **哨兵日志**: 关键上下文读取点加哨兵日志（如 `[AI-STRAT-1-SCOPE] 向量化跳过（配置不可用）: docId=... reason=状态冲突`），运行态可见。
3. **会红的测试**: 每个上下文依赖必须有正例 + 反例测试，证明「上下文传递正确 + 丢失时 fail-fast」。

## 四、反模式 ③ 多套闸不同步（M-Root-12，新元根因）

### 定义
系统同时存在多套校验闸（路由级 / 按钮级 / 拦截器级 / 黑名单级），但各闸之间**无单一事实源、无优先级声明、无同步测试**，导致闸间行为不一致。

### R182 实证：三套权限闸各自为政
| 闸 | 配置 | 消费者 | 当前状态 |
|---|---|---|---|
| 路由级 `meta.authority` | `IpdPersonType[]` | `ipd-guard.ts:55-59 hasAuthority()` | ✅ 真消费（空数组放行） |
| 路由级 `meta.access` | 权限码字符串数组 | **无** | ❌ 装饰性 |
| 按钮级 `v-access:code` | 权限码字符串字面量 | `accessStore.accessCodes` + 指令 | ⚠️ 仅超管生效 |

- **闸间不同步**: 路由级放行（`meta.authority = []`）但按钮级拦截（`canCreateBid` 自判定）；路由级 `meta.access` 装饰性但按钮级 `v-access:code` 真消费。
- **后果**: 任何登录用户都能进 `/ipd/bids` 路由，但按钮可见性由组件内自判定控制——**三套闸行为不一致**。

### R184 实证：SSRF 校验链三套优先级未对齐
| 闸 | 配置 | 优先级 | 当前状态 |
|---|---|---|---|
| 黑名单 | `ai.blocked-hosts` | 先检查（throw） | ❌ 优先级错 |
| allowlist | `ai.allowed-hosts` | 后检查 | ❌ 被黑名单先拦截 |
| DNS rebinding | 内置校验 | 最后检查 | ⚠️ 被 allowlist 跳过（设计正确但无显式声明） |

- **闸间不同步**: 黑名单先拦截 127.0.0.1，但 allowlist 后检查已晚——**三套闸优先级未对齐**。
- **后果**: 合法路径（127.0.0.1 mock）被拦，配置存在但优先级错。
- **修法**: allowlist 优先检查（host 等值匹配，命中即跳过黑名单 + DNS rebinding）。

### 修复模式
1. **单一事实源**: 所有闸共用同一份权限码常量（如 `permissions.ts`），不允许各闸自定义。
2. **优先级声明**: 多闸并存时显式声明优先级（如 allowlist > 黑名单 > DNS rebinding），写在代码注释 + 文档。
3. **会红的测试**: 每个闸必须有正例 + 反例测试，闸间同步测试（如「路由级放行 + 按钮级拦截」必须有用例覆盖）。

## 七、适用边界与不适用范围

- **适用**: 前端仓所有 IPD 视图与路由；后端仓所有 IPD 模块的拦截器 / 守卫 / 校验链；任何写「配置/拦截器/守卫/校验链」的 PR。
- **不适用**: 平台 admin 模块（`monitor/logininfor` 等），走的是 Platform 包络与 vben 原生权限体系，accessCodes 真含业务权限码（`monitor:logininfor:remove` 等），与 IPD 三套体系不互通。
- **不替代**: 后端 RBAC（Spring Security + IPD RBAC）的最终鉴权；前端任何一套闸失效时，后端仍是最后一道防线。
