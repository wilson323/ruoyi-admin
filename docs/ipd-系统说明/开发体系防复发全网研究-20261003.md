# IPD 开发体系防复发研究

研究日期：2026-10-03。范围：本项目工程助手、IDE、工作树、构建、验证与交付；涉及业务智能体时保留既有 ProjectAgent/AgentScope 单轨及人工业务批准。本文是研究交付，不是新的执行计划，不表示相关工具已安装或治理措施已生效。

## 裁决

**现有证据不支持“安装某个体系、Harness、Skill 或 MCP 后，全部异常永久消失”。** 可以对已明确的错误建立可测试的阻断条件，可以降低未知错误的发生率和影响，但不能由有限测试证明所有未来业务行为都正确。Google 的发布工程资料明确保留了测试之后的真实环境观察与回滚阶段。[发布工程](https://sre.google/sre-book/release-engineering/)、[金丝雀发布](https://sre.google/workbook/canarying-releases/)。

本项目根本缺口是：目标、源代码、构建候选、加载实例、业务效果和“完成”声明之间，尚未形成统一且经过反例验证的证据链。增加指令数量和代理数量不能自动补齐这条链。推荐复用现有 ai-native-sdlc、总画布、事项镜像与验证脚本，补充确定性门禁和独立证据核查，不另起开发体系。

## 为什么更多工具仍会假绿

IDE hook 的语义不同。Codex 官方明确说明 hooks 不是完整强制边界；部分专用路径及已有执行会话存在覆盖限制。Claude Code 部分 hook 的错误和超时会继续执行，阻断取决于事件与返回语义。Cursor 的 `failClosed` 默认关闭；权限类非法 JSON/Schema 又有单独阻断行为。因此不能拿同一脚本直接套三个 IDE，并假定效果一致。[Codex hooks](https://developers.openai.com/codex/hooks)、[Claude Code hooks](https://code.claude.com/docs/en/hooks)、[Cursor hooks](https://cursor.com/docs/hooks)。

GitHub 条件跳过的 job 可以显示成功；依赖失败导致的后续跳过也可能漏掉必需检查。最终聚合 job 必须实际执行，并核对预期子任务、退出状态、非空报告和候选身份。工作流整体因路径过滤被跳过的 Pending 与 job 被跳过的 Success 不应混为一谈。[必需状态检查故障排查](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)。

验证器也会有缺陷：OPA 官方提供 `--fail-on-empty` 防止没有测试却成功；Maven Failsafe 的集成测试结果需要走到 `verify`，且无测试默认不一定失败。需要测试门禁自身，而不是只测试业务代码。[OPA testing](https://www.openpolicyagent.org/docs/policy-testing)、[Failsafe verify](https://maven.apache.org/components/surefire/maven-failsafe-plugin/verify-mojo.html)。

## 异常机制与对应防线

| 异常机制 | 应建立的控制 | 能证明什么与不能证明什么 |
|---|---|---|
| 错仓库、旧目录、旧包、脏工作区 | 候选清单绑定仓库、基线、实际内容摘要、依赖锁、构建环境、产物摘要与加载实例 | 身份一致；不证明业务正确 |
| 工作树隔离但共用 target、端口、数据库 | 独立输出目录与资源租约；共享实例由单一集成入口装载 | 避免已识别资源碰撞；worktree 本身不隔离外部资源 |
| 退出非零被吞、全局错误漏计 | 原始退出码优先；超时、崩溃、解析失败、未知格式均失败；诊断按身份比较 | 阻断已列反例；解析规则仍须维护 |
| 空测试、跳过 job、伪覆盖率 | 必需套件非空、执行清单完整、最终聚合严格核验；覆盖率从实际分母计算 | 验证规定检查发生；数量不等于质量 |
| 文档过期、需求或权限混入 | AGENTS 做导航；唯一计划与业务合同；冲突检测及版本对应 | 发现已编码冲突；不能保证模型理解全部语义 |
| 并行代理越界、互相覆盖 | 预先分配 allowedPaths、变更所有权及依赖；集成候选重新验证 | 控制修改归属；子代理“成功”不替代回读 |
| 局部测试成功但真实装配失败 | 测试最终包、真实 HTTP、浏览器与数据库效果；证据必须同候选 | 证明验收场景；不是所有未知场景 |
| SDK 返回被误当业务完成 | 执行、待批准、业务效果、失败恢复分别判定；完成必须有效果回执 | 防止已知终态混淆；结构化回答不等于效果 |
| 崩溃重试重复写入 | 稳定效果键、接收端去重、版本/并发约束及不确定效果对账 | 约束重复效果；持久化编排不自动提供恰好一次 |
| MCP 目录 ID、权限或工具属性被误信 | 服务端校验业务身份及目录映射；限制真实文件、网络、数据库权限 | 约束实际调用；协议字段不能授予业务批准 |
| 自评、日志摘要、重新跑绿掩盖失败 | 独立验证器查原始结果、保留全部尝试、门禁反例评测 | 提高可追溯性；独立模型仍可能误判 |

以上为全范围设计目标；文末列明本轮已实现的工程子集，其余不能当作已生效。

## Skill 与 MCP 的边界

Skill 标准主要规定知识和脚本的组织格式；`allowed-tools` 还是实验字段，各宿主实现有差异。格式正确不表示行为已验证。[Agent Skills 规范](https://agentskills.io/specification)。

MCP roots 依赖服务端遵守与校验，不是操作系统沙箱；OAuth 资源与 token audience 保护连接，不替代 IPD Person、项目成员及业务批准。工具的只读、破坏性、幂等注解只是提示，不能信任不可信服务端自报。[MCP roots](https://modelcontextprotocol.io/specification/2025-11-25/client/roots)、[MCP 授权](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)、[工具注解边界](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/)。

ClawHub 的安全扫描与 SkillHub 的评级适合筛选，不替代本项目的隔离测试。Tencent SkillHub 插件安全说明明确：它不审计包内脚本；分发方评分不能证明 IPD 适配。没有理由为了本任务直接执行市场安装脚本。[OpenClaw 安全说明](https://docs.openclaw.ai/help/faq/security-and-access-control)、[Tencent SkillHub 安全说明](https://raw.githubusercontent.com/Tencent/skillhub/main/dsh-plugin/SECURITY.md)。

持久化运行仍可能重放副作用。Temporal 的至少一次执行需要稳定幂等键及接收端去重；LangGraph 检查点也要求副作用设计幂等。不能因接入它们便声称恰好一次，更不能额外建立第二条业务写入轨。[Temporal 活动执行](https://learn.temporal.io/tutorials/python/standalone-activities/)、[LangGraph Functional API](https://github.com/langchain-ai/docs/blob/main/src/oss/langgraph/functional-api.mdx)。

## 最小整合方案与信任边界

1. 修复并反例测试现有类型检查、覆盖检查和 CI 聚合入口，优先消灭可复现假绿。
2. 统一候选清单：实际源码快照 → 构建产物 → 加载实例 → 同版本验收结果。任何输入或产物变化都使旧验收失效。
3. 工作者使用独立工作树及输出目录；共享资源有租约。独立验证器读取原始产物、HTTP、业务数据库状态，并由集成入口控制加载。
4. 完成判断从模型叙述改为结构化证据判定；运行结束、待批准、业务完成、恢复结果分别记录。现有 AgentScope 官方能力继续按项目目标接入，业务权限仍由原有闸门控制。
5. 把历史真实失败转为固定评测集，测试门禁能否抓住失败、恢复是否造成重复效果；保留第一次失败和重试结果，不能以最后一次成功覆盖不稳定性。

这些是现有总计划的适配建议，不是本文授权的新执行轨。研究不改变业务审批、不关闭或降级 AgentScope 官方能力、不授权自动提交或生产写入。

**所谓硬阻断必须有信任前提。** 当执行者拥有宿主机全部权限、能够编辑验证器或绕开装载入口时，hook、包装脚本甚至自签清单都可被绕过。真正加强约束需使验证器、策略和准入入口由受保护身份掌管，并限制工作者能力；即便如此，只能保证所定义不变量和受覆盖路径，不能保证所有业务语义正确。当前环境没有完成这种权限隔离验证，因此本文不称“不可绕过”。

OpenAI 的 Harness 实践强调简短导航、版本化知识和机械检查，同时仍描述持续修复与未知长期效果；不应将其组织实践包装成通用零错误保证。[Harness engineering](https://openai.com/index/harness-engineering/)。Anthropic 强调评估最终环境结果，且独立评估者只能降低自评偏差；本项目应核对真正业务状态而不是助手声称成功。[Agent evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)、[长任务 Harness](https://www.anthropic.com/engineering/harness-design-long-running-apps)。

## 实施后必须通过的反例验收

| 注入场景 | 预期结果 |
|---|---|
| 命令退出 1、OOM、超时、全局 TS 错误、未知诊断格式 | 完成门禁拒绝；保留原始输出 |
| 必需测试为空、条件跳过、依赖失败、报告缺失 | 聚合拒绝，不显示业务验收成功 |
| 删除一个旧诊断同时引入一个新诊断 | 新诊断被识别，不因数量相同放行 |
| 源码、锁文件或包摘要在验收后变化 | 旧证据失效，重新建立候选 |
| 验证器只打开了报告但未检查内容 | 不构成完成证据 |
| 两个代理写同文件或共用构建输出 | 所有权或资源租约拒绝/串行化；不会静默互覆 |
| 旧包仍占用端口，源码测试已通过 | 加载身份不匹配，拒绝已生效声明 |
| SDK 返回非空但运行仍待批准 | 不判业务完成 |
| 写入前后崩溃、重复恢复、响应丢失 | 重复效果被约束；不确定状态进入对账 |
| MCP 自报只读但试图越权、编号来自另一目录 | 实际权限与目录校验拒绝 |
| 用户权限在运行期间撤销 | 效果提交时重新校验，不能凭旧上下文放行 |
| 重试后通过但首次失败 | 两次尝试均保留，单独报告不稳定性 |

实施验收应同时测试允许的合法路径，防止门禁“全部拒绝”形成另一种假正确。报告没有给出臆造成功率，也没有将未运行的反例写成通过。

## 补充研究：持续反思与受控进化

研究来源核对日期：2026-10-03。以下是现有开发体系的增强建议，不增加第二套 IPD 业务执行内核，也不代表这些外部工具已安装或本项目闭环已运行。

**反思必须产生可以执行的反例和候选补丁，不能只产生更长的提示词。** OpenAI 于 2026-05-11 发布的迭代修复示例，将审查、修复和执行验证分开，并用结构化输出交换结果、限制每轮修复范围。可直接借鉴为“原始失败 → 根因假设 → 最小补丁 → 原反例复测 → 既有成功路径回归”，超过本项目有依据的重试次数就保留失败并停止该节点。[OpenAI 迭代修复示例](https://developers.openai.com/cookbook/examples/codex/build_iterative_repair_loops_with_codex)。

**自动生成评测不等于自动验证候选。** OpenAI 于 2026-05-12 发布的 improvement loop 示例串联 traces、反馈、评测和 Codex；但正文明确其 Promptfoo gate 给既有 trace 输出评分，验证未来 Harness 版本必须改为实际运行候选的 provider，人仍可以校正弱评测。因此本项目不能把“评分旧日志成功”写成“新 Skill/新工具已验证”。示例使用合成财务资料及实时模型调用，不能直接证明 IPD 工程质量。[OpenAI Agent Improvement Loop](https://developers.openai.com/cookbook/examples/agents_sdk/agent_improvement_loop)。

**评测必须同时看执行过程和最终环境结果。** Anthropic 2026-01-09 的方法区分 task、trial、grader、transcript 与 outcome，并要求多个 trial；模型说成功与数据库存在最终结果是不同证据。IPD 对确定性的目录、诊断、产物摘要和业务状态优先用代码判定；模型评估只用于根因候选、可读性及难以机械判定的语义，不可覆盖确定性失败。[Anthropic Agent Evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。

**GEPA 是可测的候选优化器，不是安全批准器。** 当前核对 DSPy 文档带版本路径 `3.4.0`，说明 `dspy.GEPA` 用文本反馈优化指令，内部使用 `gepa-ai/gepa`；GEPA 官方仓库可依据执行轨迹、错误和指标提出并筛选文本/代码候选。适合后续隔离试验检索策略、Skill 表述、工具说明和检查器候选。其 benchmark 与展示指标不外推到 IPD；训练样本与独立验收样本必须分开，安全和业务权限不能成为可优化参数。此次未锁定 GEPA 包发布版本或安装它，实施前需锁定真实 release/commit 与依赖。[DSPy 3.4.0 教程](https://dspy.ai/3.4.0/tutorials/gepa_ai_program/)、[GEPA 作者仓库](https://github.com/gepa-ai/gepa)。

**Reflexion 提供错误反馈记忆的研究原型，不能作为工程不再复发的证明。** 作者仓库对应 NeurIPS 2023 论文，覆盖其研究实验。可借鉴“下一次尝试读取经过证据验证的失败教训”，不照搬全局自动记忆，也不把一次基准改善当作本项目的稳定能力。[Reflexion 作者源码](https://github.com/noahshinn/reflexion)。OpenAI 2025-11-04 的 Self-Evolving Agents 合作方 recipe 当前已标记 archived，且说明生产需要更多护栏与人工批准；因此只作为版本化候选、评分和恢复历史的概念参考，不能当作最新现成生产组件。[已归档自进化示例](https://developers.openai.com/cookbook/examples/partners/self_evolving_agents/autonomous_agent_retraining)。

### 本项目可执行闭环

1. 每个真实失败绑定候选身份、原命令、退出码、原始诊断、最终环境结果及脱敏证据；模型只能提出有来源的根因假设。
2. 将失败转为固定反例，另保留合法正例和独立验收样本；根因修复首先证明旧版本失败、新候选通过，不能靠重试直到绿。
3. 自动反思产生局部工程候选；只允许改进当前授权范围内的检索、工具策略、项目 Skill 草案及验证器，不修改业务审批、权限、安全规则或验收标准来提高分数。
4. 独立验证读取实际候选和原始证据；在原反例、既有回归、隔离副作用与运行身份检查通过后，才按现有工程授权启用候选。全局 Skill 升级仍遵循其单独授权边界。
5. 保留基线、补丁、版本摘要与全部尝试；启用后以同一候选观察复发和新回归，出现关键退化恢复上一版本，并把新失败加入反例集。

这些节点复用现有总计划和证据入口。无需引入 DSPy、GEPA、OpenAI SDK 或新 MCP 才能先做起来；现有 Python、类型检查、Vitest、构建与业务回读可以实现最小确定性闭环。外部优化器应在基础门禁可信后才隔离评估。自动反思提升候选发现速度，独立验证和受保护准入约束可覆盖错误；二者都不能承诺未知错误为零。
